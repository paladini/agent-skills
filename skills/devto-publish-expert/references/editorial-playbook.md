# DEV.to Editorial Playbook

## Choose the strongest format

| Reader need | Recommended format | Core structure |
| --- | --- | --- |
| Complete a task | Tutorial | Outcome, prerequisites, steps, verification, troubleshooting |
| Understand a decision | Engineering explainer | Tension, mental model, options, tradeoffs, recommendation |
| Evaluate a tool | Evidence-led launch | Problem, why existing options fell short, demo, limits, try it |
| Learn from real work | Case study | Context, constraint, decision, implementation, result, lessons |
| Debate a practice | Technical argument | Thesis, strongest evidence, counterargument, boundaries, action |

## Build an honest high-potential article

High-performing developer articles tend to make their value legible quickly. Optimize the controllable factors:

- recognizable problem;
- specific outcome;
- credible evidence;
- low-friction examples;
- distinctive firsthand insight;
- useful title and cover concept;
- scanning-friendly structure;
- a discussion prompt that experts can answer substantively.

Do not manufacture urgency, controversy, scarcity, or certainty.

## Title patterns

Use a subject plus a concrete benefit, constraint, or tension.

- `Build X With Y: A Practical Guide`
- `How I Solved X Without Y`
- `X vs. Y for Z: The Tradeoffs That Matter`
- `I Built X to Fix Y — Here Is What I Learned`
- `Stop Doing X Blindly: Measure Y First`

Avoid empty superlatives such as “ultimate,” “revolutionary,” or “you won't believe.” Avoid titles that omit the technology merely to create a curiosity gap.

## Opening pattern

In roughly 80–150 words:

1. name the reader's situation;
2. show the cost or missed opportunity;
3. promise the concrete result;
4. state what the tutorial will build or teach.

Skip autobiography unless it supplies essential evidence.

## Tutorial body

- Put prerequisites before the first command.
- Prefer a minimal working path before optional enhancements.
- Explain code immediately after the relevant block.
- Use realistic sample inputs and expected outputs.
- Add a verification section readers can reproduce.
- Include likely failure modes where they naturally occur.
- Mark placeholders, pseudocode, untested variations, and platform-specific commands.
- Mention security boundaries around credentials, publication, deletion, and other external effects.

## Tag strategy

Choose exactly four tags in this order of reasoning, not necessarily display order:

1. **Subject:** the central problem, such as `ai`, `webdev`, or `opensource`.
2. **Technology:** the concrete stack, such as `typescript`, `python`, or `ruby`.
3. **Format/audience:** use `tutorial`, `beginners`, or `productivity` only when the article earns it.
4. **Discovery niche:** the specific ecosystem or practice, such as `mcp`, `devtools`, or `seo`.

Check that removing any selected tag would make the article less accurately classified. If not, replace it.

## Final pass

- Read only the title, opening, headings, and conclusion. They should tell a coherent story.
- Execute or validate commands when access to the project is available.
- Remove repeated claims and generic transitions.
- Replace unsupported adjectives with evidence.
- Check links, code fences, image alt text, and secret placeholders.
- Confirm exactly four unique tags and draft status.
